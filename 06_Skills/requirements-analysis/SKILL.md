# requirements-analysis（要件整理）

## 目的

曖昧な依頼を、**検証可能な要件**へ整理する。目的・スコープ・機能／非機能要件・対象外・未解決を分けて言語化する。

## 使うとき

- 依頼の目的やスコープが曖昧なとき
- タスクの受入条件を確定させたいとき
- 実装の前に「何を作るか」を固めたいとき

## 入力

- 依頼文（`00_Inbox/` など）、プロジェクト文脈（`01_Projects/`）、関連成果物

## 手順

1. **目的**を1〜2文で言語化する（誰の・どの課題を・どう解決するか）。
2. **対象ユーザー／利用文脈**を特定する。
3. **スコープ**を「やること／やらないこと」に分ける。曖昧な広がりを断つ。
4. **機能要件（FR）**を番号付きで列挙する（FR-1, FR-2, …）。
5. **非機能要件（NFR）**を分けて列挙する（性能・セキュリティ・可用性・アクセシビリティ等）。
6. **対象外**を明記して期待値を揃える。
7. 確定できない点は**未解決の論点**に集約する（推測は「推測」と明示。`source-verification` 併用）。

## 出力テンプレート

```
1. 目的
2. 対象ユーザー / 利用文脈
3. スコープ（やること / やらないこと）
4. 機能要件（FR-n）
5. 非機能要件（NFR-n）
6. 対象外
7. 未解決の論点
8. 引継ぎ
```

## チェックリスト（完了前）

- [ ] 目的が1〜2文で言えているか
- [ ] スコープの「やらないこと」を書いたか
- [ ] FR と NFR を分離したか
- [ ] 仮の数値・前提を「推測」と明示し「未解決」に置いたか
- [ ] 受入条件に落とせる粒度になっているか

## よくある落とし穴

- 目的を書かずに機能一覧から始める（何のためかが失われる）。
- 「やらないこと」を書かず、スコープが無限に広がる。
- 仮の性能値・しきい値を根拠なく確定として書く → 「未解決」に置き推測と明示。
- FR と NFR を混ぜ、非機能の抜けに気づけない。

## 禁止・エスカレーション

- 推測で要件を確定しない。要件を勝手に追加・削除しない。
- 必須情報が欠けて判断できないときは `blocked` にして人間へ確認する。
- 判定は Checker が「適合/不適合/判定不能」で行う。自分で受入条件を緩めない。
