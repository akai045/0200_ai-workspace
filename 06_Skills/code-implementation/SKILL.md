# code-implementation（実装）

## 目的

開発ブランチ内で、**小さく安全な変更**としてコードを実装する。動くこと・壊さないこと・後から読めることを優先。

## 使うとき

- コード実装、ツール作成、バグ修正タスク（担当：build-doer）

## 入力

- 要件・受入条件、対象コード、既存のコード規約・制約（例：無クラウド・単一ファイル等）

## 手順

1. 既存コードのパターン・命名・スタイルを読み、それに合わせる。無ければ制約（§プロジェクト）から方針を決める。
2. **開発ブランチ**で作業（保護ブランチへ直接 push しない）。
3. 変更は小さく刻む。1変更＝1目的。
4. 受入条件を満たす最小実装から始める（YAGNI）。要件にない機能を足さない。
5. テストまたは動作確認を同伴（`qa-testing` と併用）。
6. 受入条件を「適合/不適合/判定不能」で自己確認してから `checking` へ。

## 出力

- 実装コード＋動作確認、作業要約（現状課題〜引継ぎの番号付き構造）。

## 制約・設計判断の記録

実装中に下した判断（ライブラリ選定・回避策・仮定）は成果物か `10_Runs` ログに残す。
例：
- 「`file://`/UNC はブラウザが直接オープンを制限 → 代替手段を併設」
- 「無クラウド方針のため外部リソースを取得せず、ローカルで完結する代替手段を採用」

## チェックリスト（完了前）

- [ ] 既存パターン／制約に沿っているか
- [ ] 受入条件を満たす最小実装か（余計な機能を足していないか）
- [ ] 動作確認またはテストをしたか
- [ ] 外部通信・秘密情報・破壊的操作を含めていないか（含むなら T2 → 停止）
- [ ] 下した設計判断を記録したか

## よくある落とし穴

- 既存規約を読まずに自己流で書く。
- 要件を勝手に拡張して肥大化させる。
- 環境依存（改行・パス・オフライン制約）を見落とす。
- 「動いたはず」で動作確認を省く。

## 禁止・エスカレーション

- 本番反映・削除・破壊的操作・認証情報変更・外部送信はしない（人間承認が要る T2）。
- 判断できない依存・権限不足は `blocked` にして人間へ確認。
