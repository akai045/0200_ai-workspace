# ui-ux-review（UI/UX レビュー）

## 目的

画面・フローの UI/UX を評価し、**現状課題 → 設計方針 → 構成 → 実装優先順位**の形に整理する。
装飾ではなく**課題起点**で、実装に落とせる粒度の提案を出す。

## 使うとき

- UI改善案、UX分析、画面仕様の言語化タスク
- フェーズ1の主対象：個人用タスク管理アプリの UI 改善案

## 入力

- 対象画面（スクリーンショット等、タスクの `inputs:`）
- 想定ユーザーと利用文脈（`01_Projects/` のプロジェクト文脈）
- 既存の用語・レイアウト規約（あれば）

## 評価軸（この観点で課題を洗う）

1. **視認性・情報階層**：重要な情報が埋もれていないか。スケール対比があるか。
2. **緊急度／状態の可視化**：締切・残量・進捗などが直感的に分かるか。
3. **次の一歩の明確さ**：ユーザーが迷わず着手できるか（次アクションの明示）。
4. **並び・フィルタの妥当性**：自動で前面に出すべきものが出ているか。
5. **状態設計**：空／読み込み中／エラー／超過などの状態が定義されているか。
6. **アクセシビリティ**：色だけに依存していないか、コントラスト、キーボード操作。

## 手順

1. 想定ユーザーの**主要タスクフロー**を1本引く。
2. 上の評価軸でフローを歩き、**現状課題を5項目以内に絞る**（多すぎる指摘は優先順位を殺す）。
3. 各課題に対する**設計方針**を短く述べる（なぜ効くか＝根拠。`source-verification` と併用）。
4. **改善画面の構成**を、要素・配置・状態が分かる粒度で書く。
5. **実装優先順位**を「効果 × コスト」で付ける（低コスト・高効果を先頭に）。
6. 検証していない前提は**「未解決」に明記**して引き継ぐ（推測で確定しない）。

## 出力テンプレート

```
1. 現状課題（5項目以内）
2. 設計方針
3. 構成（改善画面）
4. フロー
5. 例外・状態設計
6. 実装優先順位
7. 未解決 / 引継ぎ
```

## チェックリスト（完了前）

- [ ] 現状課題は5項目以内か
- [ ] 各改善案に「なぜ効くか」の根拠があるか
- [ ] 改善画面の構成が要素・状態まで書けているか
- [ ] 実装優先順位が付いているか
- [ ] 検証できていない前提を「未解決」に明記したか

## よくある落とし穴

- 見た目の刷新（色・装飾）に寄り、課題解決になっていない。
- 課題を10個以上並べ、優先順位が埋もれる。
- 空／エラー／超過などの**状態設計を忘れる**。
- しきい値（例：残日数の色分け）を仮のまま「確定」と書いてしまう → 「未解決」に置く。

## 禁止・エスカレーション

- 実画面や必須入力が無いときは、その旨を明記して進めるか、必須なら `blocked` にする。
- 受入条件を自分で緩めない。判定は Checker が「適合/不適合/判定不能」で行う。
