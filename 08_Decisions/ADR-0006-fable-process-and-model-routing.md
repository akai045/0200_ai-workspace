## 1. 依頼と結論（先に要点）

依頼：動画の手法をAILOOPに織り込みたい。ただし「いきなり変えて壊れる」のは困るので**設計から**。**既に織り込み済み／織り込むと無理が生じる箇所は正直に教えてほしい**。

結論（3手法の判定）：

| 動画の手法 | AILOOPでの現状 | 判定 |
|-----------|----------------|------|
| **① プロセス > モデル知能**（ループ構造こそがモート、モデルは労働力兼メンター） | constitution 原則1・2・6・7、SPEC §2 の根幹思想そのもの | **ほぼ完全に既済**。動画はAILOOPの賭けを外から追認しているだけ。新規作業は不要 |
| **② Fable Mode = 5ゲート**（スコープ／証拠／対立的推論／検証／校正をスキル化） | 4ゲートは既存部品に対応（下表）。実ギャップは**「対立的推論（事前の欠陥先読み）」1点**、「校正」が部分的 | **大半が既済**。ただし「動画のまま新スキル1枚で全タスクに一律適用」は**2点で無理が生じる**（§4）。分解して最小追加すれば織り込める |
| **③ エフォート最適化＋モデルルーティング**（Opusをオーケストレータ、単純作業をHaikuへ、ルーティング表で約3倍のコスト削減） | 素地あり（SPEC §7 の `model:` 別名、§4.2 のティア可変、§8 のトークン比率指標、P2-6 コスト記録）。だが**ルーティング表そのものは未整備** | **最も追加余地が大きい**。制約2（コスト）に直結。ただし品質・自律LOOP・エフォートのモデル依存で注意点あり（§4） |

**要するに：①は「もうやっている」、②は「部品はほぼ揃っていて足りないのは1ピース」、③は「素地の上に表を1枚足すのが本命」。** どれも "作り直し" ではなく "既存への最小追記" で足りる。それがAILOOPの原則7（証拠で育てる）とも合う。

## 2. 動画3手法の要約（提供内容の再掲）

1. **モデルの知能より「プロセス」が重要**：性能そのものより、どう制御しどんなループを組むかがモート。高性能モデルを「労働力」だけでなく「メンター（思考プロセスの教師）」として使う。
2. **Fable思考の抽出 = Fable Mode（5ゲート）**：スコープ設定／証拠の重視／対立的推論／検証／校正。スキルファイル化して低コストモデルに適用すると精度が上がる。
3. **エフォートレベル最適化＋モデルルーティング**：タスクに応じてエフォートを選び、Opusをオーケストレータ、単純作業を軽量モデルへ振る「ルーティング表」でコストを約3倍削減。

## 3. 現状マッピング（技法別・既済/ギャップ/衝突）

### 3.1 技法① プロセス > 知能 — 既済

- AILOOPは初手から「エージェント＝文脈・権限の隔離装置、専門性はスキル」（原則1・2）、「検査は既定1回・証拠で育てる」（原則6・7）という**プロセス中心設計**。モデルは差し替え可能な別名（SPEC §7 `model: haiku|sonnet|opus`）扱いで、思想は完全に一致。
- 「メンターとして使う」観点だけは明文化されていない（今は成果物生成にモデルを使うが、"良い思考プロセスをモデルに教わって skill/ADR に蒸留する" という運用は暗黙）。**任意の軽い追記候補**だが必須ではない。

### 3.2 技法② Fable Mode の5ゲート — 4つは既済・1つがギャップ

| Fableゲート | AILOOPの既存対応 | 状態 |
|------------|------------------|------|
| スコープ設定 | タスク frontmatter（objective/acceptance_criteria/prohibited/tier）＋ `requirements-analysis` ＋ `task-decomposition`（雛形） | **既済** |
| 証拠の重視 | `source-verification`（事実/推測/意見の3分類・一次/二次の格付け・「根拠なし記述率」指標§8）。まさにこれ | **強く既済**（背骨スキル） |
| **対立的推論** | **該当スキルなし**。Checker は存在するが *事後* の検査であって、*着手前に計画の欠陥を先読みする* ステップは無い | **実ギャップ（唯一）** |
| 検証 | Checker（受入条件の3値判定）＋ `qa-testing` ＋ 完了条件の自己確認 | **強く既済** |
| 校正 | 実運用では code-review / simplify 相当を随時実施。だが 06_Skills には無く、恒常ステップとして明文化されていない | **部分的**（暗黙運用） |

→ **Fable Mode は "新概念" ではなく、AILOOPが既に分解して持っている工程の言い換え**。純粋な不足は「対立的推論（プレモータム）」の1点、次点で「校正の明文化」。

### 3.3 技法③ エフォート／モデルルーティング — 素地あり・表が未整備

既にある素地：
- SPEC §7：各エージェントは `model:` を性能クラス別名で持つ（現状 knowledge/build/checker=sonnet、auditor=opus）。**差し替え前提の設計**。
- SPEC §4.2：「可能ならモデルティアも変える（Checker=標準、Auditor=高性能）」と**すでにルーティングの思想を明記**。
- SPEC §8：「入出力トークン比率」を監視指標に採用済み。
- P2-6：コスト記録の慣習（10_Runs JSONL）が完了済み＝**削減効果を実測できる土台がある**。

未整備：
- 「ティア／タスク種別 → 推奨モデル別名 ＋ エフォートレベル」の**ルーティング表が無い**。今は各エージェント定義に固定値が1つ書いてあるだけ。
- 「エフォートレベル」という語がドキュメントに存在しない（Opus 4.x の機能）。

## 5. 設計提案（安全・段階的・既存への最小追記）

### 提案1：Fable 5ゲートを「ティア連動チェックリスト」として織り込む（新スキルは作らない）

- 5ゲートを**独立スキルにせず**、次の2箇所へ薄く織り込む：
  - **不足ピース＝対立的推論（プレモータム）**：着手前に「この計画はどこで壊れるか／受入条件を満たさないとしたら何が原因か」を3点だけ挙げる短いステップ。置き場所の候補は (a) 未使用の `task-decomposition` スキルを "分解＋プレモータム" に格上げして埋める（§12ゲートを踏まない＝既存7枠の充実）、(b) `knowledge-doer` / `build-doer` の「着手時ステップ」に3行追記。**推奨は (a)**（スキルは着脱式で、必要なタスクだけ読み込める＝原則2に忠実）。
  - **校正**：明文化は任意。恒常ステップにすると原則6と競合するので、**T2のみ必須／T1は任意**とする。
- **ティア連動の濃度**（原則6・制約3を守る）：
  - **T0**：スコープ（＝objective/受入条件）＋証拠（source-verification）のみ。対立的推論・校正は課さない。
  - **T1**：上記＋**対立的推論（3点プレモータム）**＋検証（Checker必須は既存どおり）。
  - **T2**：上記＋校正＋Auditor（既存どおり）。
- 効果：Fableの思考規律を、AILOOPの信頼勾配に**溶かし込む**。新しい人格もスキル枚数増もゼロ。

### 提案2：モデル/エフォート・ルーティング表を新設（07_Policies 配下）

- `07_Policies/model-routing.md`（新規・ポリシー文書1枚）に「ティア × タスク種別 → 推奨モデル別名 ＋ エフォート」の表を置く。SPEC §7 の `model:` 別名運用・§4.2 のティア可変思想の**具体化**であり、思想の新設ではない。
- 保守的な初期案（例・確定ではない）：

  | タスク種別 / 工程 | 既定モデル | エフォート | 備考 |
  |------------------|-----------|-----------|------|
  | 定型・機械的（整形・リンク検査・一覧集計・Markdown整合） | haiku | low | 品質劣化が出たら sonnet へ戻す |
  | 標準実装・調査・要件整理（Doer本体） | sonnet | medium | 現状維持 |
  | 設計・アーキ判断・難所デバッグ | opus | high〜 | 判断の質が効く所だけ上げる |
  | Checker（検証） | sonnet | medium | 相関故障回避のため Doer と別ティアを維持（§4.2） |
  | Auditor（T2監査） | opus | high | 現状維持 |

- **導入の作法（原則7）**：表を作っても**既定は据え置き**。まず1〜2タスクで「haiku+low」を試し、§8指標（差戻し率・再実行回数・トークン比率）で品質を確認 → 悪化しなければ既定に昇格。効かなければ表から外す。
- エフォートは「対応モデルのみ有効・非対応は無視」と注記（壊さない）。

### 提案3（任意）：モデルを「メンター」として使う運用の明文化

- 難所で上位モデルに解かせた思考を、その場限りにせず **skill / ADR / タスクのメモに蒸留**して次回から低コストモデルでも再現できるようにする、という運用メモを constitution か skills の README に1段落追加（技法①の唯一の未明文部分）。**優先度低・任意**。

## 8. 帰結

- 動画の3手法は AILOOP と**思想レベルで衝突しない**。①は既済、②は1ピース不足、③は表1枚の追加が本命。
- 唯一気をつけるのは「動画のまま丸ごと・全タスク一律・新スキル1枚・Haiku即振り分け」という素朴な入れ方で、それは AILOOP の minimalism・ティア・証拠駆動・品質優先を壊す。本設計は**ティア連動化・既存への吸収・保守的既定＋実測監視**でそれを回避する。
- 次の区切り：この設計の**方向性の承認**。承認が出た項目だけ §7 の後続タスクで最小実装する。
